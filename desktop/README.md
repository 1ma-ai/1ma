# 1ma Desktop

1ma Desktop — приложение bb Desktop, собранное под брендом 1ma. Код bb здесь не
хранится: сборка берёт точный выпуск bb, накладывает короткую серию правок из
`patches/`, подменяет иконки на ассеты 1ma и переименовывает bb в 1ma в видимых
строках (`rebrand/`, ADR-0005). Так устроены, например,
ungoogled-chromium и сборки Linux-дистрибутивов: видно ровно то, что мы
изменили, а переход на новый выпуск bb сводится к смене тега.

## Файлы

- `upstream.json` — репозиторий bb, тег выпуска и коммит, на который он
  указывает. Скрипт откажется собирать, если тег сдвинули.
- `patches/` — правки 1ma в формате `git format-patch`, по одной теме на
  файл. Каждая правка держит тесты bb зелёными.
- `scripts/prepare.mjs` — готовит дерево для сборки: скачивает выпуск bb,
  применяет правки, подменяет иконки, переименовывает bb в 1ma и сверяет
  результат с описью, пишет `1ma-provenance.json`. `--no-rebrand` готовит
  дерево без переименования, `--update-rebrand-lock` перезаписывает опись.
- `rebrand/` — правила переименования и опись строк, см. `rebrand/README.md`.
- `package.json` — инструменты подготовки (TypeScript для разбора исходников
  bb) и тесты правил: `pnpm --filter 1ma-desktop-tooling run test`.

## Что меняют правки сейчас

1. Имя приложения 1ma, идентификатор `ai.1ma.desktop`, имена установщиков и
   исполняемых файлов, канал обновлений `1ma-ai/1ma`.
2. Данные в `~/.1ma`, чтобы 1ma и bb жили рядом; телеметрия выключена.
3. Аккаунт getbb.app, облачный ИИ bb и bb connect выключены по умолчанию.
4. Неподписанная сборка для Mac обновления не ставит сама, только проверяет,
   есть ли новая версия (`desktop-version.json` в выпуске `desktop-latest`):
   установить обновление без подписи Apple macOS не даст.
5. Заголовок окна и имя веб-приложения 1ma.
6. Сборка без сертификата Developer ID подписывается ad-hoc: без подписи
   вовсе Mac на Apple Silicon называет скачанное приложение повреждённым.
7. Просьба поставить звезду репозиторию bb на GitHub (плагин GitHub Star,
   появился в bb 0.49) выключена по умолчанию.
8. У встроенных плагинов значок приложения, а не аватар bb на GitHub.
9. Сервер обновляет себя из выпусков 1ma, а не пакетом `bb-app` из npm (там
   это пакет самого bb): версию берёт из `server-version.json` в выпуске
   `desktop-latest`, пакет `1ma-server-<версия>.tgz` — из выпуска
   `desktop/v<версия>`, сверив с его `SHA256SUMS`. Переменная
   `ONEMA_UPDATE_COMMAND_PREFIX` запускает `npm install` обновления через
   обёртку, например через лимит ресурсов.
10. С `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` (в окружении или в `env`
    пользовательских настроек, с учётом `CLAUDE_CONFIG_DIR`) Claude Code
    расход подписки у Anthropic не запрашивает и повторяет старый кэш, поэтому
    цифры устаревали и пропадали после сброса окна. Вместо них сервер пишет,
    где задана переменная, и советует `DISABLE_TELEMETRY=1`: она выключает
    телеметрию без этого побочного эффекта. Пустое значение, как и у Claude
    Code, не считается. Проверено на Claude Code 2.1.322; при смене поведения
    Claude Code правку пересмотреть.

Иконки берутся из `brand/` и `plugins/1ma-brand/assets/` (см.
`scripts/prepare.mjs`).

## Собрать

Сборка идёт в GitHub Actions, файл `.github/workflows/desktop.yml`: на
каждый пуш в `desktop/`, `brand/` и ассеты бренда, а также вручную. Готовую
сборку публикует отдельный ручной запуск `.github/workflows/desktop-release.yml`
с номером запуска сборки: он выкладывает установщик в пред-релиз без
повторной сборки.

Тот же запуск собирает сервер 1ma для Linux: пакет `bb-app` из того же
дерева (правки, ассеты, переименование), проверенный проверкой
`smoke:tarball`, которой bb проверяет свой пакет перед публикацией в npm.
В выпуске это файл `1ma-server-<версия>.tgz`: его ставят
`npm install <файл>` в пустой каталог и запускают
`node_modules/.bin/bb-app` на Node 24. Команда пока называется `bb-app`
(переименование CLI — этап 3), данные — в `~/.1ma`.

Версия сборки — следующий патч выпуска bb с пометкой запуска, как у ночных
сборок bb: bb 0.49.0 в запуске 123 (попытка 1) даёт `0.49.1-1ma.123.1`
(`scripts/version.mjs`, ставит её `scripts/bump-version.mjs` самого bb). Она
новее выпуска bb, на котором собрана, и всех прежних сборок 1ma и старше
следующего выпуска bb, поэтому проверки версий в bb работают как есть. Выпуск
называется `desktop/v<версия>`, а `desktop-release.yml` после публикации
переписывает в выпуске `desktop-latest` файлы `desktop-version.json` (его
смотрит приложение) и `server-version.json` (его смотрит сервер), только
вперёд: старую сборку поверх новой он не объявит. Выпуск `desktop-latest`
мейнтейнер создаёт один раз: `gh release create desktop-latest --prerelease`.
Выпуски идут по одному, а уже опубликованный файл выпуска не заменяется:
совпадающий пропускается, отличающийся останавливает выпуск. Упавшую сборку
перезапускать целиком (Re-run all jobs): у каждой попытки свой номер версии,
и сборку, где у приложения и сервера разные версии, выпуск не опубликует.

Для движка плагинов bb версия `0.49.1-1ma.*` выглядит как 0.49.1: плагин,
которому нужен bb не ниже 0.49.1, поставится и на сборку из 0.49.0. От
несовместимого API защищает отдельная проверка версии SDK плагина.

Если установка обновления сервера не удалась (очередь heavy занята дольше
пяти минут, сбой сети), автоматически эту версию сервер больше не пробует до
следующей сборки; поставить её можно вручную: `bb updates app apply`.
Скачивание идёт через `fetch` Node: за прокси нужен `NODE_USE_ENV_PROXY=1`.

Если коммит сборки меняет файлы `.github/workflows/`, GitHub не даёт
встроенному токену создать на нём релиз (HTTP 403). Тогда пред-релиз создаёт
мейнтейнер своим токеном: тег на коммит сборки
(`git push origin <коммит>:refs/tags/desktop/v<версия>`) и
`gh release create <тег> --verify-tag --prerelease`, а повторный запуск
`desktop-release.yml` загружает в него файлы и переписывает `desktop-latest`.

Локально подготовить дерево:

```sh
node desktop/scripts/prepare.mjs --out /tmp/1ma-desktop
```

## Изменить правку или добавить новую

1. Подготовить дерево без переименования:
   `node desktop/scripts/prepare.mjs --out /tmp/1ma-desktop --no-rebrand`.
   Ветка `1ma-patches` в нём указывает на последнюю правку серии. Поверх неё
   лежат только подменённые иконки, они не закоммичены и в правки не входят:
   добавлять в коммит только свои файлы (`git add <файлы>`, не `git add -A` и
   не `git commit -a`).
2. Работать как в обычном репозитории bb, один коммит на тему, сообщение
   начинается с `1ma:`. Чтобы изменить существующую правку, собрать серию
   заново от тега: `git cherry-pick` правок по порядку, нужную — с
   `--no-commit`, поправить и закоммитить с её сообщением (`git commit -C`).
3. Поправить тесты bb, которые проверяют изменённое поведение, в той же правке.
4. Выгрузить серию заново (старые файлы серии предварительно удалить):
   `git format-patch --no-numbered --no-signature --zero-commit -o desktop/patches <tag>..HEAD`.
   Без номеров в теме письма неизменённые правки выгружаются байт в байт.
   Дерево с переименованием для этого не подходит: его последний коммит —
   само переименование, и правки поверх него не применятся к bb.
5. Запушить: сборка проверит, что правки применяются, и соберёт приложение.

## Перейти на новый выпуск bb

Обновить `tag` и `commit` в `upstream.json`. Если правка не применяется,
подготовить дерево на старом теге, перенести коммиты на новый тег
(`git rebase`), решить конфликты и выгрузить серию заново.

Что проверить после переноса, кроме конфликтов (так шёл переход с 0.48.1 на
0.49.0):

- новые места с каталогом данных `.bb`, идентификатором `dev.bb.desktop` и
  адресами обновлений bb: правка применилась, а bb добавил то же самое в
  новом файле;
- новые встроенные плагины и их состояние по умолчанию
  (`apps/server/src/services/plugins/builtin-registry.ts`): облачные службы
  bb и реклама bb должны быть выключены;
- дифф описи построчно: каждая новая строка должна читаться правильно, а
  ошибки правил исправляются записями в `rules.json`, а не в правках.

Импорт данных из bb в 1ma работает, только если версия 1ma не ниже версии bb,
из которого сделан экспорт, поэтому 1ma не должен отставать от bb, которым
пользуются на той же машине.

## Переезд с bb на 1ma на одной машине

bb и 1ma хранят базу и настройки отдельно (`~/.bb` и `~/.1ma`), поэтому переезд
— это копия, и к bb можно вернуться. Делает её
`desktop/scripts/migrate-from-bb.mjs`, штатными командами bb:

1. bb запущен. Команда включает в bb эксперимент «Server move» (он только
   разрешает экспорт и перенос) и пишет экспорт сервера командой
   `bb server export`:

   ```sh
   node desktop/scripts/migrate-from-bb.mjs export --out ~/1ma-migration/bb-server.tar
   ```

   В экспорте есть секреты, он не зашифрован: хранить у себя и удалить,
   когда 1ma заработает.

2. Сразу после экспорта полностью остановить bb (на Mac — выйти из
   приложения, на Linux — остановить сервис). Всё, что сделано в bb после
   экспорта, в 1ma не попадёт: если bb записал файлы тредов позже экспорта,
   импорт откажет (`--archive-is-current`, если ничего важного не менялось).
3. Команда ставит экспорт в `~/.1ma` командой `bb server import` самого 1ma и
   докопирует то, чего в экспорте нет: личность машины (`host-id`,
   `auth.json`), файлы тредов, локальные плагины и машинные данные плагинов:

   ```sh
   node desktop/scripts/migrate-from-bb.mjs import --archive ~/1ma-migration/bb-server.tar --cli <bb.js из 1ma>
   ```

   Скрипт проверяет, что экспорт сделан этим же bb на этой же машине, что
   bb и 1ma не запущены и ни один процесс не держит файлы в их папках.
   Занятую папку `~/.1ma` он откладывает в сторону только с `--move-aside`;
   если импорт не удался, он возвращает её на место, а написанное сохраняет
   как `~/.1ma.failed-<время>`. `--dry-run` показывает план без изменений.

4. Запустить 1ma. При первом запуске он завершает импорт и переписывает
   пути плагинов с `~/.bb` на `~/.1ma`. Проверить `bb plugin list`: плагин,
   установленный из рабочей папки треда внутри `~/.bb`, после импорта ищется
   в `~/.1ma` и не загрузится — его надо поставить заново из его папки.

С той же личностью машины треды остаются на этом компьютере, а не на
выключенной «копии» в списке машин.

Рабочие папки не копируются, потому что база хранит их пути: рабочие деревья
git, личные рабочие папки и проекты, которые bb клонировал сам
(`~/.bb/checkouts`). 1ma работает в них на старом месте и, архивируя тред,
удаляет его рабочее дерево там же. Поэтому `~/.bb` нельзя удалять, пока
используется 1ma.

Свои папки, которые кто-то положил в `~/.bb` (не bb), скрипт не копирует и не
трогает. Пока их службы работают, он откажет; их надо штатно остановить на
время импорта, а потом они работают на старом месте. Если плагин находит такую
папку через папку данных или установлен из неё, перед первым запуском 1ma
нужна ссылка `~/.1ma/<папка>` → `~/.bb/<папка>`: импорт переписывает пути
плагинов внутри `~/.bb` на `~/.1ma`.

bb connect в копии выключен, пока не выполнить `bb server allow-connect
--data-dir ~/.1ma`; это делается, только когда bb больше не запускается, иначе
два сервера будут отбирать друг у друга туннель. Облачные плагины bb в 1ma по
умолчанию выключены.

Версия 1ma должна быть не ниже версии bb, из которого сделан экспорт. На
Mac скрипт запускается без отдельного Node:
`ELECTRON_RUN_AS_NODE=1 /Applications/1ma.app/Contents/MacOS/1ma migrate-from-bb.mjs ...`,
CLI 1ma лежит в
`/Applications/1ma.app/Contents/Resources/app.asar.unpacked/node_modules/bb-app/dist/bb.js`
(пошагово: `docs/runbooks/mac-from-bb-to-1ma.md`). Сервер 1ma на Linux
версии 0.49.0 и старше запускают с `--no-in-app-updates`: иначе обновление
из приложения поставит вместо него bb из npm
(`docs/runbooks/linux-from-bb-to-1ma.md`). Начиная с 0.49.1-1ma.* сервер
обновляется из выпусков 1ma, и флаг не нужен.

Вернуться к bb: остановить 1ma и запустить bb. Его база такая, какой была при
экспорте, а рабочие папки общие и выглядят так, как их оставил 1ma.
Автоматизации bb при запуске могут догнать пропущенные запуски, а машины,
подключённые к bb, подключаются к тому серверу, который сейчас запущен.

Проверено на Linux: экспорт bb 0.47.1, импорт в 1ma 0.49.0 из сборки CI,
проект, тред, его рабочее дерево и плагин из папки данных на месте, машина
та же, bb после этого запускается на своих данных.

## Тесты bb, которые падают не из-за 1ma

`Desktop bb tests` гоняет тесты bb без изменений. Бывает, что тест выпуска
bb падает на раннерах GitHub, а в CI самого bb проходит: там другой git и
машины быстрее. Такой тест записывается в `known-test-failures.json` с
причиной, только если он падает и в базовом прогоне без переименования
(ручной запуск `desktop-tests.yml` с `rebrand=false`). Серия с таким тестом
проходит, а сам тест по-прежнему запускается и виден в логе предупреждением;
любое другое падение валит серию. В списке записан тег bb, для которого его
проверили: после перехода на новый выпуск серия падает, пока каждую запись
не пересмотрят (обычно bb к тому времени уже чинит тест, и запись
удаляется) и не обновят тег.
