# 1ma Superagent

Серверный плагин 1ma: запись работ по чатам и PR на двух серверах 1ma и
действия Главного бота. Устройство и причины — в
[ADR-0006](../../docs/adr/0006-superagent.md), проект этапа 1 — в
[docs/plan/2026-11-14-superagent-stage-1.md](../../docs/plan/2026-11-14-superagent-stage-1.md).

## Как работает

- Роль `control` (сервер Mac): проход раз в минуту (`* * * * *`), сразу после
  загрузки плагина и после событий местных чатов (`thread.idle`,
  `thread.failed`, `thread.created`, `thread.archived`, `thread.unarchived`,
  `thread.deleted`, `interaction.pending`). Поводы, пришедшие во время
  прохода, объединяются в один следующий проход с сохранением области.
- Каждый исполнитель (свой сервер, другой сервер по HTTP) отдаёт снимок с
  полнотой: `complete`, `partial` или `failed`. Чат, пропавший из полного
  списка, получает состояние `closed`; из неполного — остаётся как был.
- Работа — верхнеуровневый видимый чат владельца, созданный не плагином и не
  являющийся чатом Главного бота.
- Причина ожидания работы: `owner` — у чата ожидающий вопрос; `limit` — в
  очереди повтор хода после сбоя провайдера (`provider-retry`); `machine` —
  ход держит `concurrency-limit` или машина не в сети. Очередь чата
  читается только у чатов с `queuedWork: "waiting"`.
- Роль `executor` (сервер Linux, значение по умолчанию): проходов нет. Роль
  `control` выбирается явно и ровно на одном сервере: свежая установка не
  делает проходов, пока её не настроили.

## Исполнители

- `local` — свой сервер через `bb.sdk`: `threads.list` (живые чаты, скрытые
  включительно), `environments.list`, `projects.list`.
- `remote-http` — второй сервер по адресу из настройки: `GET /api/v1/threads`
  (`archived=false&includeHidden=true`, постранично), `GET /api/v1/environments`
  (постранично), `GET /api/v1/projects`. Каждый ответ проверяется схемой.
- Страница — 200 записей, не больше 25 страниц; на страницу 10 секунд, на весь
  список 30. Первая страница не пришла — `failed`, следующая — `partial`, упёрлись
  в предел страниц — `partial`. Окружения или проекты не пришли — снимок
  `partial`: ветки и репозитории неизвестны, но чаты не закрываются.

## Заявка PR и связь с чатом

- Чатам проектов из настройки **Watched repositories** (кроме **Excluded
  projects**) `configure` добавляет инструмент `sa_claim_pr` и одну строку
  инструкции. Так на обоих серверах.
- `sa_claim_pr({ url })` проверяет, что проект чата — репозиторий PR и что он
  не исключён, и пишет заявку в метаданные чата (пространство
  `1ma-superagent`): репозиторий, номер, ветка окружения в момент заявки.
- Сервер `control` раз в проход читает заявки чатов обоих серверов
  (`experimental_listPluginMetadata` у себя, `POST /threads/plugin-metadata` у
  второго) и проверяет каждую по GitHub: проект чата равен репозиторию PR,
  проект и PR не исключены, PR не из форка, автор — аккаунт GitHub сервера
  чата, ветка заявки равна ветке PR, заявка сделана не раньше открытия PR.
  Одна действительная заявка — связь `claim` с пометкой «заявлено чатом»
  (`basis: "claimed by the chat"`), а не «проверено»: это адрес доставки
  замечаний, а не доказательство авторства. Две заявки или ни одной — PR
  непривязанный, вопрос владельцу; отказ — причина сохраняется.
- Связь по заявке хранит время последнего подтверждения (`confirmedAt`). Если
  в проходе чат связи не прочитан — он архивирован, его сервер не ответил или
  чтение метаданных частично упало, — связь остаётся с прежней отметкой.
  Снимается она только после того, как метаданные этого чата прочитаны и
  заявки в них нет или она больше не проходит проверку.
- Ручная связь (`manual`, «задано владельцем») сильнее заявки.
- Происхождение PR в первом выпуске всегда «неизвестно» (`provenance:
"unknown"`): ни заявка, ни текущая модель чата его не доказывают. Модель
  чата, пока PR связан заявкой, показывается отдельно как «заявлено чатом»
  (`chatModels`), пропуск наблюдения отмечается. Доказательство по
  конкретному коммиту — этап 2.
- GitHub читается через `gh api` в хост-части плагина на основной машине
  сервера: недавно изменённые PR (до трёх страниц по 50 от курсора, впервые —
  за 7 дней) и известные PR по номеру, пока открыты и сутки после закрытия.

## Главный бот

- Чат Главного бота в первом выпуске — только закреплённый чат из настройки
  **Main bot chat**. Шов `bots.v1.forThread` для плагина `1ma-bots` описан в
  ADR-0006 и включится вместе с ним; чаты с `originPluginId` `1ma-bots`
  инструментов бота не получают. Карточки и инструменты адресуются одному и
  тому же закреплённому чату.
- Одно правило исключений (`isExcludedRepo`) действует везде: выдача
  инструментов и инструкций в `configure`, выполнение инструментов (бот,
  заявка, запуск чата, отправка запуска) и чтение связей PR. Закреплённый
  чат бота в исключённом проекте не получает ни инструментов, ни инструкции,
  а вызов отклоняется; связь PR исключённого репозитория не видна в
  `work.v1` и у бота и не участвует в вопросах.
- Только на сервере `control`. Действия «читает»: `sa_overview` (серверы,
  работы, непривязанные PR, ожидающие) и `sa_work_detail({ ref })`. В ответах
  только проверенные идентификаторы (репозиторий `owner/name`, номер PR,
  коммит, `сервер:thr_…`, провайдер и модель по шаблону), перечислимые
  состояния и коды ошибок. Заголовки чатов, адреса git, ветки, тексты ошибок,
  заголовки карточек и детали журнала модели не отдаются; не прошедшее
  проверку поле — `null`. Подробности владелец читает через `work.v1`.

## Вопросы владельцу

- Проход только ставит вопрос в таблицу `questions` (ключ, тема, ожидаемая
  версия темы, карточка, приоритет); живой вопрос с тем же ключом второй раз
  не ставится.
- Диспетчер держит в чате Главного бота одну открытую карточку
  (`bb.ui.requestInput`, слот `pendingInteraction` с id `question`) и пишет,
  сколько ещё ждут. Карточка: что наблюдается, что затронуто, рекомендация,
  один-три варианта, рекомендуемый — первый.
- Ответ принимается, только если карточка открыта этим экземпляром плагина
  (токен совпадает), вариант есть на карточке и версия темы не изменилась;
  иначе вопрос `stale` или снова ждёт. Принятие ответа и его действие — одна
  транзакция базы плагина. Кнопка карточки сначала пишет решение через
  `questions.v1.decide` (по id вопроса и токену) и только после успеха
  закрывает карточку штатным ответом. `questions.v1.decide` — единственное
  место, где ответ становится решением: штатный ответ (`respond`) только
  закрывает карточку. Если к нему уже записано решение, остаётся записанное,
  что бы ни пришло в закрывающем ответе. Если записи нет (ответ пришёл мимо
  кнопки, из другого клиента), ничего не выполняется: вопрос возвращается в
  очередь и показывается снова с пометкой, что ответ не записан и его нужно
  дать кнопкой. Остановка плагина сразу после такого ответа оставляет вопрос
  открытым; после перезапуска он показывается снова. Карточка, открытая на
  уже записанном решении (`questions.v1.state`), показывает его и
  закрывается сама.
- У вопроса есть срок (7 дней от постановки): после него ответ не
  принимается, вопрос `expired` и заново не открывается; карточка, закрытая
  по сроку, тоже `expired`.
- После перезагрузки плагина или перезапуска сервера открытая карточка
  открывается заново с новым токеном; ответ на старую не принимается.
  Закрытая владельцем карточка — `canceled`.
- Ответ на карточку не доказывает, что ответил сам владелец: сервер не
  сообщает, кто ответил. Для решений по чувствительным выпускам карточка не
  используется.
- Первый вид вопроса — PR без заявки от аккаунта из настроек, дольше 10 минут:
  привязать к чату с той же веткой (адрес замечаний, происхождение остаётся
  неизвестным) или оставить непривязанным. Перед записью ручной связи ответ сверяется с
  настоящим: PR открыт и наблюдался не позже 10 минут назад, выбранный чат не
  закрыт, наблюдался так же недавно и его проект — репозиторий PR, проект не
  исключён. Иначе связь не пишется, вопрос `stale`.

## Запуск чата через бота

- `sa_start_chat({ server, projectId, providerId, model, prompt, title? })`
  только предлагает: пишет действие `proposed` с неизменяемыми параметрами и
  ставит вопрос с текстом поручения дословно. Вызов возвращается сразу.
  Проект из исключённых — отказ.
- «Запустить» в одной транзакции с ответом переводит действие в `confirmed`;
  «Не запускать» — в `canceled`.
- Проход захватывает действие одним обработчиком (`confirmed` → `sending`) и
  создаёт чат с `originPluginId: "1ma-superagent"` и меткой
  `{ spawn: { nonce } }`: случайное значение, которое плагин хранит у себя и
  не отдаёт ни одним RPC и ни одним инструментом. Ответ — `bound`; отказ
  сервера 400, 401, 403, 404 или 422 — `failed`; любой другой ответ, таймаут
  и обрыв — `unknown`. Действие `sending`, оставшееся от прежнего экземпляра
  плагина, — `unknown`.
- Для `unknown` каждый проход ищет чат по метке, скрытые и архивные
  включительно. Найденный чат засчитывается, только если он в проекте
  действия на его сервере и создан не раньше отправки (с допуском 2 минуты
  на расхождение часов серверов): один — `bound`, несколько — `ambiguous` и карточка. Через 10
  минут — вопрос: «Подождать 30 минут» (рекомендуется) или «Запустить заново»
  с предупреждением. Новый запуск — новое действие с новой меткой, старое
  `canceled`; если чат старого появится позже, его очередь удаляется, он
  останавливается, и владелец получает карточку. Остановка считается
  сделанной, только когда стоп прошёл и очередь чата после него пуста; до
  этого действие — `stopping late`, владелец видит карточку «остановить пока
  не удалось», и каждый проход повторяет стоп и проверку. Шаги, которые чат
  успел сделать до остановки, она не отменяет. Автоматического повтора
  запуска нет.
- Чаты, созданные так, входят в запись работ как `bot-request`.

## Итог задачи бота

- Для привязанных чатов, запущенных ботом (последние 7 дней), проход читает,
  когда чат не работает: ожидающий вопрос исполнителя (`interactions`), иначе
  последний `turn/completed` (готово, упала, остановлена) и для «готово» —
  `output`, обрезанный до 600 символов.
- Ключ итога — действие, завершённый ход (или вопрос) и вид результата; он
  записывается в `reports` вместе с карточкой одной транзакцией, поэтому
  повторный проход вторую карточку не создаёт.
- Итог показывает карточка в чате бота с вариантом «Понятно»; модель бота при
  этом не запускается, и текст исполнителя к ней не попадает.

## Коммит в `main` мимо поезда

- Ошибка чтения журнала (в том числе отказ RPC хоста) не обрывает проход:
  состояние чтения журнала пишется отдельно (`work.v1.list` → `journal`), а
  шаги после полного прохода — вопросы о PR, действия, проверка `main`,
  итоги задач и показ карточек — выполняются независимо друг от друга.
- Включается настройкой **Check main against the release train** (по
  умолчанию выключена). Путь к журналу задаёт не сервер, а сама машина: тот,
  кто ставит плагин, пишет его в `settings.json` каталога данных хост-части
  (`<каталог данных 1ma>/plugins/1ma-superagent/host-data/settings.json`,
  `{"trainJournal": "/абсолютный/путь/journal.jsonl"}`). RPC хоста пути не
  принимает. Хост проверяет фактический путь: ссылка, ведущая из каталога
  журнала, и не обычный файл отвергаются. Читаются последние 2 МБ журнала.
- `gh` хост вызывает сам: сервер передаёт только операцию (PR, список PR,
  голова `main`) с репозиторием `owner/name`, номером PR или страницей, а
  запрос `GET` строит хост.
- Из журнала берутся только записи `author: "release-train"` с репозиторием
  (`repo` или `repository`), попыткой (`attempt` или `attempt_id`), событием
  (`event` или `type`), `final_sha` и `base_sha`; остальные строки
  пропускаются. Поля настоящего журнала на Mac ещё не сверены, поэтому
  проверка по умолчанию выключена.
- Сначала читаются головы `main` всех репозиториев через `gh`, затем журнал:
  журнал не старше голов. Первая увиденная голова — точка отсчёта.
- Каждое движение `main` должно продолжать цепочку журнала: от новой головы
  по записям `merged` (`final_sha` → `base_sha`, не больше 20 шагов) до
  прежней известной головы — норма, новая голова становится опорной.
  Поезд, собранный поверх головы, которую не писал поезд, означает прямой
  коммит между проходами — карточка «Коммит в main мимо поезда».
  `push-intent` без `merged`, запись `merged` без `base_sha` или неполный
  хвост журнала без нужной записи — «нужна сверка» (данные, без вопроса).
- Откат (`rolled-back`) применяется только к переходу от головы, которую
  записала откатанная попытка. Новая голова после такого перехода становится
  опорной только после ответа владельца на карточку «Это откат поезда?»: «да»
  — норма, «нет» — обход поезда. До ответа — «нужна сверка».

## RPC на чтение

- `work.v1.list({ limit?, offset?, includeClosed? })` — работы, новые первыми,
  состояние серверов, GitHub и `main` репозиториев.
- `work.v1.get({ workId })` — одна работа и её сервер; неизвестный id —
  отказ `not_found`.
- `work.v1.waiting(null)` — работы, которые ждут владельца, и вопросы в очереди.
- `work.v1.pullRequests({ unlinkedOnly? })` — известные PR со связью и её
  основанием.
- `work.v1.actions({ limit? })` — действия бота (запуск чата): состояние,
  попытка, чат; без текста поручения.

## Выключение плагина

- `dispose` прерывает текущие запросы и дожидается конца идущего прохода,
  поэтому его записи попадают в базу до её закрытия. Выключенный экземпляр не
  захватывает новых действий; создание чата, прерванное выключением, остаётся
  «исход неизвестен» и находится по метке следующим экземпляром. Ответ на
  карточку, пришедший выключенному экземпляру, ничего не пишет: вопрос
  остаётся открытым и открывается заново следующим экземпляром.
