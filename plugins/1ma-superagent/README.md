# 1ma Superagent

Серверный плагин 1ma: запись работ по чатам и PR на двух серверах 1ma и
действия Главного бота. Устройство и причины — в
[ADR-0006](../../docs/adr/0006-superagent.md), проект этапа 1 — в
[docs/plan/2026-11-14-superagent-stage-1.md](../../docs/plan/2026-11-14-superagent-stage-1.md).

## Как работает

- Роль `control` (сервер Mac): проход раз в минуту (`* * * * *`), сразу после
  загрузки плагина и после событий местных чатов (`thread.idle`,
  `thread.failed`, `thread.created`, `thread.archived`, `thread.unarchived`,
  `thread.deleted`, `interaction.pending`). Поводы, пришедшие во время
  прохода, объединяются в один следующий проход с сохранением области.
- Каждый исполнитель (свой сервер, другой сервер по HTTP) отдаёт снимок с
  полнотой: `complete`, `partial` или `failed`. Чат, пропавший из полного
  списка, получает состояние `closed`; из неполного — остаётся как был.
- Работа — верхнеуровневый видимый чат владельца, созданный не плагином и не
  являющийся чатом Главного бота.
- Роль `executor` (сервер Linux, значение по умолчанию): проходов нет. Роль
  `control` выбирается явно и ровно на одном сервере: свежая установка не
  делает проходов, пока её не настроили.

## Исполнители

- `local` — свой сервер через `bb.sdk`: `threads.list` (живые чаты, скрытые
  включительно), `environments.list`, `projects.list`.
- `remote-http` — второй сервер по адресу из настройки: `GET /api/v1/threads`
  (`archived=false&includeHidden=true`, постранично), `GET /api/v1/environments`
  (постранично), `GET /api/v1/projects`. Каждый ответ проверяется схемой.
- Страница — 200 записей, не больше 25 страниц; на страницу 10 секунд, на весь
  список 30. Первая страница не пришла — `failed`, следующая — `partial`, упёрлись
  в предел страниц — `partial`. Окружения или проекты не пришли — снимок
  `partial`: ветки и репозитории неизвестны, но чаты не закрываются.

## Заявка PR и связь с чатом

- Чатам проектов из настройки **Watched repositories** (кроме **Excluded
  projects**) `configure` добавляет инструмент `sa_claim_pr` и одну строку
  инструкции. Так на обоих серверах.
- `sa_claim_pr({ url })` проверяет, что проект чата — репозиторий PR и что он
  не исключён, и пишет заявку в метаданные чата (пространство
  `1ma-superagent`): репозиторий, номер, ветка окружения в момент заявки.
- Сервер `control` раз в проход читает заявки чатов обоих серверов
  (`experimental_listPluginMetadata` у себя, `POST /threads/plugin-metadata` у
  второго) и проверяет каждую по GitHub: проект чата равен репозиторию PR,
  проект и PR не исключены, PR не из форка, автор — аккаунт GitHub сервера
  чата, ветка заявки равна ветке PR. Одна действительная заявка — связь
  `claim`; две — PR непривязанный с причиной; отказ — причина сохраняется.
- Ручная связь (`manual`) сильнее заявки; происхождение при ней неизвестно.
  Происхождение заявленного PR — провайдер и модель чата в каждом проходе;
  пропуск наблюдения отмечается.
- GitHub читается через `gh api` в хост-части плагина на основной машине
  сервера: недавно изменённые PR (до трёх страниц по 50 от курсора, впервые —
  за 7 дней) и известные PR по номеру, пока открыты и сутки после закрытия.

## Главный бот

- Чат Главного бота — закреплённый чат из настройки **Main bot chat**, а когда
  появится плагин `1ma-bots` — его чаты с возможностью `dev`.
- `configure` выбирает инструменты бота, если чат — из настройки или его
  `originPluginId` — `1ma-bots`. Это только необходимое условие: каждый вызов
  проверяет чат ещё раз (настройка или `bots.v1.forThread` с `dev`), иначе
  отказ без чтения.
- Только на сервере `control`. Действия «читает»: `sa_overview` (серверы,
  работы, непривязанные PR, ожидающие) и `sa_work_detail({ ref })`. Ответы —
  структурированные поля без текста чатов (без заголовков).

## Вопросы владельцу

- Проход только ставит вопрос в таблицу `questions` (ключ, тема, ожидаемая
  версия темы, карточка, приоритет); живой вопрос с тем же ключом второй раз
  не ставится.
- Диспетчер держит в чате Главного бота одну открытую карточку
  (`bb.ui.requestInput`, слот `pendingInteraction` с id `question`) и пишет,
  сколько ещё ждут. Карточка: что наблюдается, что затронуто, рекомендация,
  один-три варианта, рекомендуемый — первый.
- Ответ принимается, только если карточка открыта этим экземпляром плагина
  (токен совпадает), вариант есть на карточке и версия темы не изменилась;
  иначе вопрос `stale` или снова ждёт. Принятие ответа и его действие — одна
  транзакция базы плагина.
- После перезагрузки плагина или перезапуска сервера открытая карточка
  открывается заново с новым токеном; ответ на старую не принимается.
  Закрытая владельцем карточка — `canceled`.
- Ответ на карточку не доказывает, что ответил сам владелец: сервер не
  сообщает, кто ответил. Для решений по чувствительным выпускам карточка не
  используется.
- Первый вид вопроса — PR без заявки от аккаунта из настроек, дольше 10 минут:
  привязать к чату с той же веткой (адрес замечаний, происхождение остаётся
  неизвестным) или оставить непривязанным.

## Запуск чата через бота

- `sa_start_chat({ server, projectId, providerId, model, prompt, title? })`
  только предлагает: пишет действие `proposed` с неизменяемыми параметрами и
  ставит вопрос с текстом поручения дословно. Вызов возвращается сразу.
  Проект из исключённых — отказ.
- «Запустить» в одной транзакции с ответом переводит действие в `confirmed`;
  «Не запускать» — в `canceled`.
- Проход захватывает действие одним обработчиком (`confirmed` → `sending`) и
  создаёт чат с `originPluginId: "1ma-superagent"` и меткой
  `{ spawn: { actionId, attempt } }`. Ответ — `bound`; отказ сервера `4xx` —
  `failed`; таймаут, обрыв, `5xx` — `unknown`. Действие `sending`, оставшееся
  от прежнего экземпляра плагина, — `unknown`.
- Для `unknown` каждый проход ищет чат по метке, скрытые и архивные
  включительно: один — `bound`, несколько — `ambiguous` и карточка. Через 10
  минут — вопрос: «Подождать 30 минут» (рекомендуется) или «Запустить заново»
  с предупреждением. Новый запуск — новое действие с новой меткой, старое
  `canceled`; если чат старого появится позже, его очередь удаляется, он
  останавливается, и владелец получает карточку. Автоматического повтора нет.
- Чаты, созданные так, входят в запись работ как `bot-request`.

## Итог задачи бота

- Для привязанных чатов, запущенных ботом (последние 7 дней), проход читает,
  когда чат не работает: ожидающий вопрос исполнителя (`interactions`), иначе
  последний `turn/completed` (готово, упала, остановлена) и для «готово» —
  `output`, обрезанный до 600 символов.
- Ключ итога — действие, завершённый ход (или вопрос) и вид результата; он
  записывается в `reports` вместе с карточкой одной транзакцией, поэтому
  повторный проход вторую карточку не создаёт.
- Итог показывает карточка в чате бота с вариантом «Понятно»; модель бота при
  этом не запускается, и текст исполнителя к ней не попадает.

## RPC на чтение

- `work.v1.list({ limit?, offset?, includeClosed? })` — работы, новые первыми,
  и состояние серверов.
- `work.v1.get({ workId })` — одна работа и её сервер; неизвестный id —
  отказ `not_found`.
- `work.v1.waiting(null)` — работы, которые ждут владельца, и вопросы в очереди.
- `work.v1.pullRequests({ unlinkedOnly? })` — известные PR со связью и
  происхождением.
