# 1ma Memory Gate

Плагин 1ma: новый ход чата ждёт в очереди, пока на его машине не хватает
памяти. Если память свободна — чат стартует, если нет — ждёт. Встроенный
лимит числа тредов (`concurrency-limit`) остаётся потолком; этот плагин
добавляет условие по памяти в ту же точку допуска (хук `message.dispatch`).

## Правило

Для хода `start-turn` треда, который ещё не работает, на машине H правила
проверяются по порядку:

1. Плагин выключен, у треда нет машины или это `join-turn` — ход идёт.
2. H не Linux — ход идёт. Это решает хост-часть по платформе машины, а не по
   тому, удалось ли прочитать файлы.
3. На H меньше чатов, чем **Always allow this many chats** (по умолчанию 1), —
   ход идёт без проверки памяти, даже если показаний ещё нет. Считаются треды,
   которые сервер называет работающими (`sdk.threads.listRunning()`), и треды,
   которые плагин пропустил, пока их ход ещё не начался (см. «Доли»).
   Спрашивающий тред себя не считает, каждый тред считается один раз.
4. Свежего показания со свободной памятью нет (нет вовсе, старше 15 секунд или
   без единой цифры свободной памяти) — ход ждёт, сборщик читает память сразу.
   Ход идёт без проверки, только когда выполнены оба условия: какой-то ход на
   H ждёт уже 30 секунд (отсчёт от самого раннего из ждущих) и у H 30 секунд
   нет свежего пригодного показания (последнее пригодное показание устарело
   30 секунд назад или его не было). Первый ход после затишья поэтому всё
   равно ждёт 30 секунд. Сломанное чтение памяти не держит чаты вечно: лимит
   числа тредов продолжает стеречь машину.
5. `free = min(лимит cgroup − рабочий набор cgroup, MemAvailable машины)` по
   тем значениям, что есть. Ход идёт, когда
   `free ≥ доля × (треды с долей + 1)` и давление памяти (`full avg10`) ниже
   **Memory pressure limit**; иначе ждёт с причиной вроде
   `Waiting for free memory on <машина>`. Цифр в причине нет: ждущий ход не
   спрашивается заново, пока ничего не меняется, и цифры на его карточке
   устарели бы. Живые цифры показывает `bb memory-gate status`.
6. Любая неожиданная ошибка пишется в журнал, и ход идёт: лимит числа тредов
   всё равно стережёт. Список работающих тредов ждётся не дольше 2 секунд по
   собственному таймеру плагина.

Время плагин отсчитывает по монотонным часам; перевод системных часов не
делает показание устаревшим и не открывает проход без проверки.

## Доли

Память пропущенного треда видна в показаниях не сразу, поэтому каждый тред на
H, который пропустил плагин, держит долю **Memory per chat** сверх своей.
Учёт следует за жизнью хода по событиям bb:

- Пока ход не начался (нет `thread.active`), тред держит долю и считается
  чатом на H, пока сервер называет его работающим или, если не называет, —
  не дольше 2 минут после пропуска. Предел в 2 минуты нужен только потому, что
  bb ничего не сообщает, когда пропущенный ход падает во время подготовки.
- `message.queued` для такого треда значит, что попытку придержал другой
  плагин или ядро: доля освобождается, а плагин спросят заново, когда ход
  попробуют снова. Для начавшегося хода это событие ничего не меняет.
- После `thread.active` тред держит долю, пока сервер называет его
  работающим, и не дольше 45 секунд от начала хода.
- `thread.idle`, `thread.failed`, `thread.archived` и `thread.deleted`
  снимают учёт треда сразу.

Так три чата из очереди, перепроверенные одним проходом, не видят одну и ту же
свободную память, а ход существующего чата держит долю и пока ядро готовит
его команду (вложения, подготовка машины), то есть до того, как сервер назовёт
тред работающим.

## Перепроверка

Ждущий ход сам по себе не перепроверяется: плагин не назначает `sendAt` и не
держит своего таймера. Ядро bb владеет часами и очередью, а плагин просит его
перепроверить придержанные сообщения (`experimental_hooks.recheck`), когда
меняется то, от чего зависит его ответ.

Плагин помнит треды, которым он последним ответил «ждать». Тред забывается при
любом другом ответе хука, при `message.dispatched`, `thread.active`,
`thread.archived` и `thread.deleted`. После `message.cancelled` (пользователь
удалил одну строку, другие могли остаться) тред становится сомнительным.

Проверка идёт после каждого сохранённого показания и в конце каждого обхода
сборщика, после `message.cancelled` и после изменения настроек. Если ждущих
нет, она ничего не спрашивает у сервера. Иначе она один раз читает настройки и список работающих
тредов и примеряет ответ к каждому ждущему ходу. Перепроверка нужна, если
какой-то ход прошёл бы сейчас или он сомнительный, а также если настройки или
список получить не удалось (хук в этом случае пропускает ходы, и проверка с
ним согласна; в журнал идёт одно предупреждение на всё время сбоя). Тогда плагин один раз вызывает `recheck`. Ход, который так
перепроверяли уже 10 секунд, а хук о нём не спросили, забывается: 10 секунд —
предел ядра на проход хуков, так что строка попытки, начатой до первой
перепроверки, к этому времени записана, а ушедший ход больше не
перепроверяется. Если строка осталась, хук спросят, и ход вернётся. Неудачный
вызов `recheck` ничего не меняет и пишется в журнал один раз, пока вызов не
заработает снова. Проверки не идут
параллельно: одна выполняется, ещё одна может ждать за ней.

После завершения, сбоя, архивации или удаления любого треда плагин вызывает
`recheck` всегда, как встроенный лимит числа тредов. У чата могут быть другие
сообщения, придержанные от имени плагина, о которых его заново не спрашивали
(например, второе сообщение, отправленное отдельно), а собственный разбор
очереди ядра в конце хода придержанные плагином сообщения не берёт. Если при
этом есть ждущие ходы, сборщик читает память сразу: освобождённая память видна
в новом показании, а не в сохранённом.

На `message.queued` проверки нет: долю, освобождённую так, увидит следующий
обход сборщика, и повтор не запускает следующий повтор. При старте сборщика
плагин один раз вызывает `recheck`, чтобы ходы, придержанные прежним
экземпляром плагина, спросили заново.

## Ходы без проверки

Когда на H ход впервые пропущен без проверки (правило 4), в журнал пишется
одно предупреждение. Этот период кончается, когда у H появляется пригодное
показание, снятое после его начала; это видно и при ответе хука для H, и при
проверке после обхода сборщика, так что запись о возвращении показаний
появляется, даже если ни один ход не спрашивал. Каждая запись делается один
раз за период. Машина, пропавшая из списка, выбывает из учёта без записи.

## Как читается память

Хост-часть (`host.ts`) на каждой машине Linux читает файлы ядра, каждый не
больше 64 КБ (`/proc/self/mountinfo` — не больше 1 МБ):

- группа cgroup v2 процесса: путь из строки `0::` в `/proc/self/cgroup`,
  точка и корень монтирования cgroup2 из `/proc/self/mountinfo`; каталог
  группы — точка монтирования плюс путь без корня монтирования;
- на каждом уровне от этой группы вверх до точки монтирования (не больше 64
  уровней): `memory.max`, `memory.high`, `memory.current`, `memory.stat`
  (`inactive_file`);
- машина: `/proc/meminfo` (`MemAvailable`), `/proc/pressure/memory`.

Лимит уровня — меньшее из `memory.high` и `memory.max` (литерал `max` значит
«нет лимита»), рабочий набор — `memory.current − inactive_file`, как в
Kubernetes. Уровень с конечным лимитом и читаемым `memory.current` даёт запас
`лимит − рабочий набор`; в показание идёт уровень с наименьшим запасом. Так
лимит, поставленный на предка, виден и процессу в дочерней группе без своего
лимита. Если `mountinfo` нет, он слишком велик, путь процесса лежит вне корня
монтирования или файлы группы не читаются, читается только `/sys/fs/cgroup`.

Давление берётся из `memory.pressure` уровня с наименьшим запасом, без него —
из группы процесса, а без неё — из файла машины. Отсутствующий или
испорченный файл обнуляет только то, что от него зависит; строка без
завершающего перевода строки считается обрезанной и не читается. Без
`memory.stat` рабочим набором считается весь `memory.current`. Если на Linux
не читается ничего, показание приходит без цифр, и действует правило 4, а не
правило 2.

Сервер (`server.ts`) опрашивает каждую подключённую машину примерно каждые 5
секунд (`bb.hosts.experimental_client`); насколько часто на деле, зависит от
того, отвечает ли список машин, и от паузы после неудачных чтений. Машины
опрашиваются независимо: на каждую не больше одного запроса за подключение, у
запроса и у списка машин свой срок 8 секунд. Не уложившийся запрос считается сбоем; сбой чтения машины пишется в
журнал, повторы реже (до раза в минуту), старое показание просто стареет.
Подключившаяся заново машина читается сразу, её прежняя пауза сбрасывается, а
ответ на запрос до переподключения отбрасывается. Машина, пропавшая из
списка, теряет своё показание. Пока не удаётся получить сам список машин,
показания стареют; список запрашивается в прежнем темпе, а в журнал идёт одно
предупреждение на всё время сбоя.

## Настройки

Меняются в настройках плагина в приложении или `bb plugin config`:

- **Wait for free memory** (`enabled`) — по умолчанию включено.
- **Memory per chat (MB)** (`reserveMb`) — 600, от 64 до 65536.
- **Memory pressure limit (%)** (`pressurePercent`) — 10, от 1 до 100.
- **Always allow this many chats** (`minRunning`) — 1, от 0 до 100.

Сохранённые значения проверяются при чтении; значение вне диапазона
заменяется значением по умолчанию.

## Команда

`bb memory-gate status [--json]` — для каждой машины: показание, его возраст,
сколько памяти нужно новому чату, давление, ответ для нового чата сейчас
(стартует / ждёт и почему), сколько ходов на ней ждут, и настройки. В JSON
число машин сверх показанных — поле `hiddenHosts`.

## Чего плагин не может

- Работает только на Linux; на macOS и Windows все ходы идут.
- Работающий чат никогда не останавливается.
- Кнопка **Send now** по замыслу bb обходит хуки: сообщение уходит сразу.
- Память вне контейнера видна только через `MemAvailable`.
- Пока у машины 30 секунд нет пригодного показания и какой-то её ход столько
  же ждёт, новые ходы идут без проверки; `bb memory-gate status` показывает
  это как `a new chat starts unchecked: no memory reading`.
- Пропущенный ход, который так и не начался, держит долю не дольше 2 минут:
  bb не сообщает о сбое во время подготовки хода.
- Второе сообщение в тот же чат, отправленное, пока его ход готовится, и
  придержанное в очереди (этим плагином, другим плагином или ядром),
  освобождает долю этого чата раньше времени.
- `bb memory-gate status` показывает не больше 50 машин и число остальных.

## Разработка

```sh
pnpm install            # из корня репозитория
pnpm --filter bb-plugin-1ma-memory-gate run typecheck
pnpm --filter bb-plugin-1ma-memory-gate run test
pnpm --filter bb-plugin-1ma-memory-gate run build   # bb plugin build → dist/
```

Разбор файлов (`memory.ts`) и решение (`gate.ts`) — чистые функции с
тестами; связка с bb (`server.ts`) проверяется на `createFakePluginHost` из
`@get-bb/plugin-sdk/testing`, хост-часть — на
`experimental_createHostEntryHarness` из `@get-bb/plugin-sdk/testing/host`.
Все тексты плагина — настройки, причины ожидания, вывод команды и записи
журнала — собраны в `strings.ts`.
