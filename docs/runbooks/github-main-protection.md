# Защита ветки main на GitHub

Что GitHub требует от `main`, записано в `.github/main-protection.json`, а не
только в настройках репозитория: настройки без файла не видны в ревью и
незаметно расходятся с рабочими процессами.

## Что задаёт файл

Ниже то, что записано в файле. На GitHub это действует только после того,
как скрипт это применил (`--apply`, ниже), а что действует сейчас, показывает
сверка без флага.

- В `main` попадает только то, у чего прошли обязательные проверки. Их пять:
  две задачи `CI` и по одной итоговой задаче (`… result`) у `Desktop`,
  `Desktop bb tests` и `Bots end-to-end`. Правило действует и на
  администратора.
- Историю `main` нельзя переписать (`push --force`) и ветку нельзя удалить.
- Действия в рабочих процессах указываются коммитом, а не тегом: тег владелец
  действия может передвинуть на другой код. Это проверяет и GitHub
  (`sha_pinning_required`), и тест `scripts/lib/workflows.test.mjs`.
- Обязательных ревью нет: в репозитории один участник, одобрить свой запрос
  ему некому. Ревью идёт по правилам `AGENTS.md`, а не кнопкой GitHub.
- Запрос на слияние сам по себе не обязателен: прямой push в `main` пройдёт,
  если у этого коммита уже есть все пять зелёных проверок, то есть он уже
  проверен в запросе.
- Обязательные проверки привязаны к приложению GitHub Actions, но не к
  содержимому рабочих процессов: запрос, который меняет сам процесс или его
  скрипты, проверяется изменённой версией. Такие правки смотрятся на ревью.
- Запрос, который конфликтует с `main`, не получает ни запуска, ни проверок:
  GitHub не может собрать пробное слияние. Проверки появятся, когда конфликт
  разрешён.

## Почему у трёх рабочих процессов есть задачи changes и result

`Desktop`, `Desktop bb tests` и `Bots end-to-end` нужны не каждому запросу.
Если бы они запускались только по своим путям (`paths` у `pull_request`), на
остальных запросах их проверки не появлялись бы вовсе, а обязательная
проверка, которая не появилась, блокирует слияние навсегда. Поэтому они
запускаются на каждом запросе: задача `changes` за несколько секунд смотрит,
задеты ли пути (`scripts/lib/changed-paths.mjs`), остальные задачи без этого
пропускаются, а `result` отчитывается всегда.

GitHub считает пропущенную задачу пройденной, поэтому итог выносит не он, а
`scripts/lib/workflow-result.mjs`:

- ответ `changes` должен быть буквально `true` или `false`; любой другой
  (например, после опечатки в имени output) — провал;
- пути задеты — каждая задача обязана пройти. Исключение одно и названо в
  самом процессе (`OFF_PULL_REQUESTS`): задачи, которые процесс не запускает на
  запросах (сборки `linux-server` и `macos` у `Desktop`);
- пути не задеты — каждая задача обязана быть пропущена.

Что считается «задетыми путями»: сравнивается результат пробного слияния
запроса с его базой (`HEAD^1..HEAD`), а не ветка запроса с точкой ответвления,
как делает фильтр `paths` самого GitHub. Если база и запрос независимо внесли
одну и ту же правку, для слияния это не изменение, и задачи не запускаются.

В список путей каждого процесса входит и то, чем он сам решает, запускаться
ли: его файл, оба скрипта, `.nvmrc`, если процесс берёт из него версию Node.
Процесс, который ставит зависимости pnpm в корне репозитория, спрашивает и о
том, что читает установка: `package.json` (из него и версия pnpm),
`pnpm-workspace.yaml`, `pnpm-lock.yaml`, а появятся — `.npmrc` и
`.pnpmfile.*`. Запуски на `main` по-прежнему ограничены `paths` у `push`: от
них зависят выпуски. Список путей у `push` и список в задаче `changes` обязаны
совпадать, а каждый путь сборки `Desktop` есть и у `Desktop bb tests`:
выпуск требует прогона тестов bb для того же коммита. Всё это держат тесты
`scripts/lib/workflows.test.mjs`.

Те же тесты не дают задаче пройти, когда её работа не прошла или не
выполнялась: в процессах с обязательной проверкой нет `continue-on-error`,
работа не уходит в другой процесс (`uses:` у задачи), а условие `if` у шага
есть только у шагов, перечисленных в тесте с причиной (диагностика после
сбоя и шаги отдельных шардов). Обязательная задача процесса без `changes`
ни от кого не зависит (`needs`): иначе она пропускается вместе с той, от
которой зависит, а пропущенную GitHub считает пройденной. Шаги, которые и
есть работа проверки (тесты, проверки bb, smoke-тесты), перечислены в тесте
вместе с командой, которую каждый обязан выполнять. Тест видит только текст
шага. Комментарий начинается с `#`, который открывает слово в Bash, стоит
вне кавычек и не экранирован. Дойдёт ли до команды оболочка
(`if false; then …`, `echo …`), тест не доказывает, это видно только на
ревью диффа. Задачи, которые не идут на запросах, тоже перечислены там с
причиной. Для каждого артефакта, нужного выпуску, в `desktop-release.yml`
есть ровно одна команда `gh run download` с его именем в `--name`. Каждый
артефакт выгружает ровно один шаг задач, которых ждёт итоговая задача, с
`if-no-files-found: error`, без `if` и `continue-on-error`. В его `path`
указаны нужные выпуску файлы. Строки с `!` в начале запрещены. Итоговая
задача сначала получает скрипт (`actions/checkout`), а процесс с обязательной
проверкой запускается на каждом запросе в `main` (без `paths`,
`branches-ignore` и `branches` без `main` у `pull_request`). Тест проверяет
точный набор событий: `pull_request_target`, `merge_group`, `workflow_call`
и `workflow_run` туда не входят, а у `Bots end-to-end` есть ручной запуск,
без которого не сделать переименование (ниже). Если такой процесс
запускается на push, у `push` есть только `branches` и `paths`; `branches`
обязательно, в нём `main` и только имена веток, без шаблонов (`*`, `?`, `+`,
`[`, `]`, `!`). Без `branches` процесс запускался бы и на push тегов, а к
тегам GitHub `paths` не применяет. У обоих процессов `Desktop` есть и `paths`,
и оба запускаются на push в `main`: без этого у сборки нет прогона тестов bb
для выпуска.

## Сверка и применение

`node scripts/protect-main.mjs` без флага ничего не меняет: читает настройки
репозитория, названного в файле, и печатает каждое расхождение строкой. Код
выхода 0 — GitHub требует то, что в файле; 1 — есть расхождения; 2 — GitHub
прочитать не удалось (нет прав, нет сети, ответ оборван или не того вида) или
GitHub отвечает за другой репозиторий; это не расхождение.

Скрипт всегда обращается к github.com (`gh api --hostname github.com`), что бы
ни было в `GH_HOST`: файл называет репозиторий на github.com. `gh` он
запускает без `GH_DEBUG` и `DEBUG`, чтобы `gh` не печатал отладочный вывод.

Первым делом скрипт спрашивает GitHub о самом репозитории и сравнивает
`full_name` из ответа с `repository` в файле: переименованный или
перенесённый репозиторий отвечает и под старым именем, через
перенаправление. Если имена разные, скрипт называет оба и останавливается,
больше ничего не читая и не записывая: имя в файле нужно исправить.

Ответ на чтение принимается, только если `gh` завершился успешно, GitHub
ответил кодом 2xx и тело — целый JSON того вида, который ждёт скрипт. Пустое
или оборванное тело — ошибка чтения, а не пустая настройка. Ветка считается
незащищённой только по ответу 404, в котором сообщение GitHub ровно
`Branch not protected`; любой другой 404 — ошибка чтения.

Скрипт проверяет ответы по правилам ниже. Если ответ прочитать не удалось,
скрипт завершает работу с кодом 2 и больше ничего не записывает.

- защита ветки — объект, его `url` оканчивается адресом, который спросил
  скрипт (`/repos/<репозиторий>/branches/<ветка>/protection`);
- у каждого поля-объекта с ключом `enabled` этот `enabled` — `true` или
  `false`; переключатель, который назван в файле, если он есть в ответе,
  именно такой объект. Переключатель, которого в ответе нет, считается
  выключенным;
- у `required_status_checks` (если он не `null`) `strict` — `true` или
  `false`, а список `checks` есть, и в каждой проверке есть имя (`context`) и
  приложение (`app_id`, число или `null`). Ответ только со старым списком
  `contexts` не прочитан: в нём не видно приложения;
- `required_pull_request_reviews` и `restrictions`, если они есть и не
  `null`, — объекты. Отсутствующее поле или `null` означает, что настройка
  выключена;
- в настройках Actions `enabled` есть и равно `true` или `false`; другие
  названные в файле поля, если есть, того же типа, что в файле. Когда Actions
  выключены, GitHub этих полей не отдаёт: это расхождение («GitHub reports no
  value»), и `--apply` его записывает;
- в ответе GraphQL `requiresDeployments` и `pageInfo.hasNextPage` — `true`
  или `false`, `mergeQueue` — `null` или объект; нет любого из них — ответ не
  прочитан;
- REST и GraphQL должны согласиться, есть ли у ветки классическое правило
  защиты. Если REST вернул объект защиты, GraphQL должен вернуть объект в
  `branchProtectionRule`. Если REST вернул 404 с `Branch not protected`,
  в `branchProtectionRule` должен быть `null`. При расхождении скрипт
  называет оба ответа.

Сверяется: настройки Actions из файла; обязательные проверки вместе с
приложением-источником; ревью и ограничения на запись; каждый переключатель
ветки, который отдаёт GitHub, включая те, что в файле не названы (они должны
быть выключены: так видны и блокировка ветки `lock_branch`, и настройка,
которую GitHub добавит позже); обязательные подписи коммитов; правила из
наборов правил (rulesets); и три вещи, которых REST-ответ о ветке не
показывает, поэтому скрипт читает их через GraphQL у того единственного
классического правила, которое GitHub применяет к ветке
(`ref(qualifiedName: "refs/heads/main").branchProtectionRule`; нет такой
ветки — сверка не удалась):

- `required_deployment_environments` — окружения, в которые правило требует
  развернуть код до слияния;
- `bypass_force_push_allowances` — кому правило разрешает `push --force`,
  хотя для остальных он выключен (REST в этом случае отвечает, что
  переписывать историю нельзя никому);
- `merge_queue` — включена ли для ветки очередь слияний: с ней обязательные
  проверки должны отчитываться и на событии `merge_group`, иначе слияния
  встают.

Не сверяется: кто может запускать процессы из форков и права токена
процессов — это отдельные настройки репозитория.

`node scripts/protect-main.mjs --apply`:

- печатает те же расхождения;
- отказывается что-либо менять, если файл в рабочей папке не совпадает с
  файлом в `main` на GitHub: применяется только слитое и прошедшее ревью;
- читает GitHub ещё раз и по этому чтению решает, что отправлять. Пишет
  только то, что расходится, по частям: настройки Actions (`actions`), список
  обязательных проверок (`required checks`, отдельным запросом, если у
  защиты ветки расходится только он) или защиту ветки целиком
  (`branch protection`), подписи (`required signatures`). Наборы правил и три
  настройки, читаемые через GraphQL, скрипт не меняет, их убирают в
  настройках;
- после каждого запроса перечитывает всё. Это чтение решает и судьбу
  запроса, и что отправлять дальше: перед каждым запросом оставшееся
  считается заново, и часть, которую GitHub уже показывает как в файле, не
  отправляется (даже если её поправил кто-то другой). Каждая часть
  отправляется не больше одного раза за запуск;
- запрос удался, когда чтение после него показывает его часть как в файле,
  каким бы ни был ответ; для списка проверок и подписей это значит ещё, что
  у ветки есть защита. Иначе запрос не удался, даже если GitHub ответил
  успехом. Ответ ненадёжен с обеих сторон: после перенаправления `gh`
  показывает ответ на GET, в который превратился запрос, а ответ на
  сделанную запись может не дойти (обрыв связи, сбой сервера по дороге, `gh`
  не закончил за минуту и остановлен);
- ответ печатается только как объяснение: код из строки статуса
  (`gh api --include`), а не из текста сообщения, и сообщение GitHub; если
  ответа нет — последняя непустая строка, которую `gh` напечатал в stderr,
  обрезанная до 300 знаков с `…`. Заголовки не печатаются. Повторов и
  ожидания нет;
- вывод говорит только о том, что видно: «Sent, and GitHub showed each as
  the file says after its request: …» — какие части отправлены и показаны
  после своего запроса как в файле (кто именно их так записал, скрипт не
  знает); часть, которую не отправляли, там не названа. Если GitHub показывает
  часть как в файле, а ответ был ошибкой, это сказано отдельно;
- на первом неудавшемся запросе останавливается, следующие не отправляет, и
  пишет «Not as the file says after it was sent: <часть>», какие расхождения
  этой части ушли со времени чтения перед запросом, какие остались, и ответ.
  Следующая строка говорит только о частях, отправленных раньше («Sent
  before it, …» или «Nothing was sent before it.»);
- в конце печатает расхождения, прочитанные после последнего запроса; код 0
  — только если их нет. Если перечитать после запроса не удалось, печатает,
  какие части отправлены раньше и показаны как в файле, и что после какого
  запроса чтение не удалось, с ответом на него; код выхода 2, и состояние
  нужно проверить сверкой без флага.

## Как менять

Новый рабочий процесс для запросов, новая задача в процессе с `changes`,
переименование задачи, новый путь — всё проверяет
`scripts/lib/workflows.test.mjs` (входит в `pnpm run check`). Если меняется
список обязательных проверок или другая настройка:

1. правка `.github/main-protection.json` идёт обычным запросом;
2. после слияния — `node scripts/protect-main.mjs --apply` из свежего `main`
   (нужен `gh` с правами администратора репозитория);
3. `node scripts/protect-main.mjs` без флага подтверждает результат;
4. открытые запросы обновляются свежим `main`, чтобы получить все проверки.

Переименование обязательной задачи одним запросом слить нельзя: GitHub ждёт
старое имя, а запрос его уже не выдаёт. Порядок из трёх запросов:

1. добавить вторую итоговую задачу с новым именем рядом со старой: те же
   `if: always()`, `needs` и шаг со скриптом вердикта. Тесты считают итоговой
   каждую такую задачу, и каждая ждёт все рабочие задачи. Слить;
2. убедиться, что новое имя свежим зелёным статусом от GitHub Actions стоит и
   на последнем коммите `main`, и на открытом запросе; только потом заменить
   имя в `.github/main-protection.json`, слить, применить, сверить. `Desktop`
   и `Desktop bb tests` получают статус на `main` сами: слияние шага 1 меняет
   их файл, и push запускает их. У `Bots end-to-end` запуска по push нет: его
   запускают на `main` вручную (Actions → Bots end-to-end → Run workflow,
   ветка `main`), а новое имя на запросе проверяют на любом открытом запросе,
   обновлённом свежим `main`;
3. убрать задачу со старым именем.

Тесты `scripts/lib/workflows.test.mjs` проходят на каждом из трёх шагов: файл
прогоняет себя целиком на снимках всех трёх шагов для каждого процесса с
`changes`, с новыми id и именем задачи, которых нет ни у одной задачи
процесса (id) и ни у одной задачи и обязательной проверки репозитория (имя).
Ещё раз целиком он прогоняет себя на трёх снимках такого переименования у
`Bots end-to-end`. Для новой задачи тесты берут `renamed_result` и
`Bots smoke result`, если они свободны, или подбирают свободные id и имя.

## Если проверка зависла и слить нельзя ничего

Скрипт из ветки не применяется, и файл в этот момент слить нельзя, поэтому
ремонт — точечный и ручной:

1. выполнить сверку и сохранить её вывод вместе с текущим списком проверок
   (`gh api repos/1ma-ai/1ma/branches/main/protection/required_status_checks`);
2. в настройках GitHub (Settings → Branches → правило для `main`) убрать только
   зависшую проверку, остальное не трогать;
3. слить исправление, из-за которого проверка зависла;
4. вернуть проверку: `node scripts/protect-main.mjs --apply` из свежего `main`
   запишет только список проверок, если у ветки есть защита и расходится
   только он; иначе он записывает защиту ветки целиком. Сверка без флага
   должна дать код 0;
5. записать в план, что было ослаблено, на сколько и почему.

Пока шаг 4 не сделан, сверка показывает расхождение — это и есть напоминание.

## Обновления действий

Dependabot раз в месяц предлагает одним запросом новые коммиты действий
(`.github/dependabot.yml`). Запрос проходит те же проверки; перед слиянием
смотрится, что изменились только строки `uses:` и что версии в комментариях
— выпуски самих действий.
