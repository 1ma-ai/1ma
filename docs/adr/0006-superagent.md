# ADR-0006. Суперагент: учёт работы по факту, вопросы владельцу, подключаемые части

Статус: черновик 2026-11-14, правка после ревью Codex

## Контекст

Владелец работает обычными чатами на двух серверах 1ma: основной сервер на
Mac и сервер на Linux, где работает Claude. Замечания и результаты между
чатами и машинами сейчас пересылаются вручную, а чат-координатор держит в
контексте модели очередь, состояние и ревью; он растёт, упирается в лимиты и
требует напоминаний. Позже суперагента получат сотрудники компаний, поэтому
части, которые у них будут другими, должны подключаться, а не вшиваться.

Сервер Linux не должен получать доступ к Mac: API сервера 1ma не имеет
аутентификации, и подключение Linux машиной сервера Mac или через bb Connect
даёт агенту на Linux полный доступ к Mac. Поэтому серверов два, и все
запросы между ними начинает Mac.

Проверки этапа 0 (временные серверы 1ma 0.49.1 и исходники bb):

- API сервера создаёт чат с `origin: "plugin"`, `originPluginId` и
  `pluginMetadata`; чат находится потом по `originPluginId` и пакетному
  чтению метаданных, архивные включительно. Чат создаётся, даже если клиент
  не дождался ответа. Ключа идемпотентности нет.
- `POST /threads/:id/stop` прерывает ход, но очередь сообщений чата
  остаётся.
- Встроенный Tasks не привязывает чаты другого сервера. Владельцу отдельная
  запись задачи не нужна: единица учёта — чат и его PR.
- Плагин может открыть форму в чате (`bb.ui.requestInput`) без хода модели;
  так же устроен встроенный инструмент вопросов. Ответ на форму не несёт
  признака того, кто ответил: интерфейс, CLI и агент для сервера одинаковы.
  Открытая форма живёт в памяти сервера и пропадает при остановке чата,
  перезагрузке плагина и перезапуске сервера.
- На Mac почти все чаты владельца (31 из 33 за месяц) идут в одном общем
  каталоге проекта, поэтому совпадение ветки не указывает на чат-автора PR.

## Решение

1. **Один плагин `1ma-superagent` на сервере Mac.** Он ведёт запись работы,
   наблюдает оба сервера и GitHub, даёт действия Главному боту. Оболочку бота
   (сущность, место в навигации, значок) делает отдельный плагин `1ma-bots`.
   Шов между ними — один метод RPC `bots.v1.forThread`: суперагент включает
   свои действия в чате бота с возможностью `dev`. Пока `1ma-bots` нет,
   Главный бот — обычный закреплённый чат, id которого задан в настройках
   суперагента.
2. **В цикле управления нет модели.** Модель нужна для разговора с
   владельцем, самой работы и ревью.
3. **Учёт по факту.** Плагин хранит, что должно произойти, читает, что есть
   на самом деле, и делает один следующий шаг. Проход запускается событием,
   когда оно есть (чат на Mac закончил ход, владелец ответил на вопрос), и по
   расписанию для того, что сообщить само не может: GitHub и сервер Linux.
   Журнала событий и очереди исходящих нет.
4. **Ядро и части.** Ядро — запись работы, проход и записи действий.
   Общие интерфейсы заводятся только там, где уже есть две реализации:
   источник работы (`WorkSource.observe` возвращает результат с полнотой и
   временем, чтобы «пусто» не путалось с «не ответил») и исполнитель (свой
   сервер через SDK, другой по HTTP). Чтение GitHub, журнал поезда и вопросы
   человеку остаются модулями до появления второй реализации. Запись работы
   хранит ссылки на источник, чат и сервер, а не поля репозитория и коммита;
   связь с PR — отдельная таблица. Запись отдаётся через RPC на чтение, чтобы
   доска или другое представление добавлялись без изменения ядра.
5. **В чат бота попадает только то, что требует владельца или что он сам
   запросил.** Отчётов «ничего не изменилось» и хода работы нет. Итог задачи,
   запущенной ботом, показывает карточка, которую рисует код, без хода модели
   бота: текст исполнителя во вход модели не попадает.
6. **Граница доверия и вопросы владельцу.** Защищаемся от текста извне
   (сервер Linux, GitHub, итоги исполнителей) и от ошибок бота. Агент с
   оболочкой на Mac может обратиться к серверу напрямую и ответить на
   карточку; сервер не сообщает, кто ответил. Поэтому ответ на карточку не
   считается доказательством личного решения владельца и для решений по
   чувствительным выпускам не используется. Вопрос владельцу — карточка с
   вариантами, её открывает код плагина; ответ приходит коду, и действие
   выполняется с параметрами, сохранёнными до вопроса. Проход только ставит
   вопрос в очередь; диспетчер держит одну открытую карточку на чат и
   открывает её заново после перезапуска. Карточка хранит цель и ожидаемую
   версию работы: устаревшая или просроченная действие не запускает.
7. **Запись действия.** Ответ владельца и запись действия с неизменяемыми
   параметрами сохраняются одной транзакцией базы плагина; отправку атомарно
   захватывает один обработчик, поэтому старая и новая версии плагина не
   выполнят её дважды. Перед созданием чата действие получает метку. Если
   ответа нет, исход неизвестен: плагин ищет чат по метке и привязывает его,
   только когда найден ровно один. Автоматического повтора нет; через
   десять минут — вопрос владельцу («подождать» или «запустить заново» с
   предупреждением, что первый запрос ещё может примениться). Чат отменённого
   действия, появившийся позже, останавливается.
8. **Граница между серверами.** Плагин на Mac обращается к серверу Linux
   только по HTTP API `/api/v1` своим небольшим клиентом со схемами на
   границе; сервер Linux к Mac не обращается. Метаданные чата может изменить
   любой клиент, поэтому они служат только для поиска после потерянного
   ответа; источник истины — таблицы плагина. Текст из чатов — данные, а не
   поручение. PR связывается с чатом заявкой самого чата (инструмент плагина,
   `threadId` даёт сервер), а не совпадением ветки: на Mac почти все чаты
   идут в одном общем каталоге. Чтобы заявить PR из чата Linux, плагин стоит и
   на сервере Linux в роли исполнителя: заявка пишется в метаданные чата на
   его сервере, плагин на Mac читает и проверяет её. Адрес доставки и
   происхождение изменений хранятся отдельно.
9. **Сквозные проверки в GitHub Actions.** На рабочей станции сервер 1ma и
   все процессы агентов делят одну группу памяти (тогда 3 ГиБ, сейчас 4,5 ГиБ);
   два временных сервера довели её до лимита, и ядро убивало процессы агентов. Проверки на
   живых серверах (два сервера, плагин, заглушка агента вместо модели, обрыв
   и задержка ответа) идут только в GitHub Actions.

## Последствия

- Этап 1 суперагента от `1ma-bots` не зависит; переход на бота из
  `1ma-bots` меняет только способ узнать чат бота.
- Выпуск bb может изменить HTTP API сервера Linux; клиент плагина проверяет
  ответы схемами, а сквозной тест на закреплённой сборке ловит это до
  установки.
- Новый источник работы или исполнитель добавляются реализацией интерфейса,
  без изменения ядра и таблиц записи работы; общий интерфейс проверки,
  действия выпуска и вопросов появляется вместе со второй реализацией.
- Сервер Linux получает тот же плагин в роли исполнителя: только заявка PR и
  инструкция о ней, без исходящих подключений.
- Отклонено: Tasks как учёт (не видит чатов другого сервера), Bots Sidebar
  (нет лицензии), подключение Linux машиной сервера Mac (снимает изоляцию),
  долгоживущий чат-координатор и мост через комментарии GitHub (состояние в
  контексте модели), подтверждение текстом в чате (модель может его
  подделать), лента автосообщений в чате бота.
