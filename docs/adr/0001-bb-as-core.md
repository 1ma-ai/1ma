# ADR-0001. bb как ядро 1ma; наслоение через плагины, а не форк

Статус: предложено 2026-10-30 (ждёт подтверждения владельца)

## Контекст

1ma строится как «операционная система бизнеса на ИИ». Владелец пользуется bb
(getbb.app, MIT) ежедневно и хочет, чтобы 1ma выглядел и работал как bb со
своими правками (шрифты, композер, сайдбар), а первой целью было полностью
заменить bb в его собственной работе (кодинг и остальные задачи).

Проверено по исходникам bb (refs/bb, main на 30.10.2026, версия 0.48.1):

- bb = server (SQLite, HTTP+WS) + host daemon (машины, окружения, процессы
  агентов) + app (React 19, Vite) + desktop (Electron) + CLI + SDK. Монорепо
  pnpm/turbo, ~800k строк TypeScript.
- Большая часть видимого интерфейса реализована как встроенные плагины, которые
  официально «форкабельны» (docs/forkable-plugins.md,
  scripts/forkable-plugins.json): composer, thread-list, navigation, memory,
  tasks, workflows, docs, side-chat, automations, все провайдеры. Копия такого
  плагина собирается вне монорепо только на опубликованном `@get-bb/plugin-sdk`
  и компонентах реестра (`@/components/ui/*`). Свой композер или свой список
  тредов выбирается в Settings → Appearance.
- Шрифты и палитра задаются CSS-темой (`bb theme`, токены `--font-sans`,
  `--font-mono`, `--font-terminal`) или манифестом плагина `bb.themes`.
- Дистрибуция: один `marketplace.json`; несколько плагинов в одном репозитории
  через `.bb/plugins.json`; релизы по git-тегам с префиксами (`composer/v1.2.0`).
- «Движки» (агенты) в bb называются providers и тоже плагины: provider-claude-code,
  provider-codex, provider-pi, provider-acp (любой агент по протоколу ACP).
- Не покрыто плагинами: логотип, имя приложения, онбординг, часть оболочки.
  Для этого нужен форк `apps/desktop` и лаунчера `packages/bb-app` (этап
  «брендированный десктоп»).

## Решение

1. Ядро bb не форкаем. 1ma на первых этапах = `bb-app` из npm без изменений +
   набор плагинов 1ma + маркетплейс 1ma + тема 1ma.
2. Всё новое делаем плагинами bb через официальные точки расширения. Там, где
   нужно изменить встроенное поведение (композер, сайдбар), берём копию
   форкабельного плагина по процедуре bb и ведём её как свой плагин с
   зафиксированным upstream-коммитом (`UPSTREAM.md` в каждом форке).
3. Брендированный десктоп (имя, логотип, установщик, предустановленные плагины)
   делаем отдельным этапом как тонкий форк `apps/desktop` + `packages/bb-app`,
   с минимальным диффом и регулярной синхронизацией с upstream.
4. Точки расширения, которых не хватает, сначала пробуем внести в upstream bb
   (issue → PR), а не обходить хаками.
5. Версию bb пиним; обновляем осознанно, с прогоном проверки форков.

## Последствия

- Плюсы: минимальная стоимость сопровождения, все улучшения bb приходят
  бесплатно, разработка плагинов не требует сборки монорепо bb (важно для
  слабой рабочей станции), каждая часть 1ma версионируется отдельно.
- Минусы: зависимость от темпа и API-стабильности bb (многие поверхности ещё
  `experimental_`); брендинг и оболочка приходят позже; часть идей потребует
  переговоров с upstream.
- Отклонено: форк LibreChat как ядро (владелец), жёсткий форк bb целиком
  (дорогое слияние, как показал опыт platform-librechat), свой сервер с нуля
  (противоречит цели «заменить bb» как можно раньше).
