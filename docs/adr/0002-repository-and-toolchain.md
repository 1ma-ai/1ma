# ADR-0002. Структура репозитория и инструменты

Статус: принято 2026-10-30

## Контекст

1ma на первых этапах = плагины bb (ADR-0001). bb устанавливает плагины из git
обычным `npm install --omit=dev --ignore-scripts` внутри каталога плагина, а
коллекцию плагинов в одном репозитории описывает `.bb/plugins.json`.
Маркетплейс bb = один `marketplace.json` с git-источниками и диапазонами
версий по тегам с префиксами.

## Решение

- Один публичный репозиторий `1ma-ai/1ma` (MIT): `plugins/<id>/` по плагину,
  `.bb/plugins.json` как индекс, `marketplace/marketplace.json` как витрина,
  `docs/{adr,plan,research}`, `scripts/` для служебных задач.
- Каждый плагин самодостаточен: свой `package.json`, зависимости только из
  npm (без `workspace:`), свой `tsconfig.json` от `tsconfig.base.json`, свои
  тесты на `@get-bb/plugin-sdk/testing`, свой `README.md`.
- Разработка через pnpm workspace (Node 24, corepack). Общие dev-инструменты в
  корне: TypeScript, vitest, oxlint, oxfmt. Сборка плагина только
  `bb plugin build` (как требует bb), в CI через закреплённую версию `bb-app`.
- Релизы: git-теги `<plugin-id>/vX.Y.Z`; `marketplace.json` ссылается на
  диапазоны, bb сам подбирает совместимую версию.
- Плагины, скопированные из встроенных плагинов bb, хранят `UPSTREAM.md` с
  коммитом bb и датой; скрипт `scripts/` показывает дрейф относительно upstream.
- Версия bb, под которую ведётся разработка, закреплена в корневом
  `package.json` (`devDependencies.bb-app`) и в `engines.bb` плагинов.

## Последствия

- Любой плагин ставится в чужой bb одной командой `bb plugin install`.
- Переименование плагина меняет его id и ломает установленные копии, поэтому
  id фиксируются заранее: новые плагины получают префикс `1ma-`
  (`bb-plugin-1ma-theme` → id `1ma-theme`); два плагина владельца пока
  сохраняют свои старые id, чтобы не терять установленные копии.

## Дополнение 2026-10-31

- Диапазон версий в маркетплейсе задаётся только мажором (`^0` сейчас, `^1`
  после 1.0). bb запоминает диапазон, выбранный при установке, поэтому узкий
  `^0.1.0` навсегда отрезал бы установленные копии от выпуска 0.2.0. Правило
  держит `scripts/check-marketplace.mjs`.
- Linux-сервер владельца (он же рабочая станция с лимитом heavy) получает
  плагины не из git, а путём из отдельного release-worktree на `origin/main`:
  `node scripts/release-linux.mjs`. Так зависимости ставятся внутри heavy, а не
  процессами сервера bb в обход лимита, и выкладка не зависит от нестабильного
  соединения этой машины с GitHub. Mac владельца и будущие пользователи ставят
  плагины из маркетплейса.
