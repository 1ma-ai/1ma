# Плагины 1ma внутри приложения: описание для согласования и ревью

14.11.2026. Владелец выбрал встроить плагины 1ma в приложение (новая правка
bb с его согласия). Это описание идёт на ревью Codex до кода.

## Цель

Поставил 1ma — и плагины 1ma на месте, на любой машине и у клиента. Они
обновляются вместе с приложением и не ставятся отдельно ни командой, ни
скриптом выкладки. Касается `1ma-brand`, `1ma-theme`, `1ma-server-switcher`,
`1ma-auto-updates`, позже `1ma-bots` и `1ma-sidebar`. `1ma-home-dashboard`
(владелец удалил его на Linux 11.11.2026) не встраивается.

## Как bb держит встроенные плагины (bb 0.49.0)

- Список — константа `BUILTIN_PLUGINS` в
  `apps/server/src/services/plugins/builtin-registry.ts` (имя, id,
  `defaultEnabled`, `autoInstall`).
- Сборка: `packages/bundled-plugins/build.ts` для каждого имени из списка
  копирует `plugins/<имя>/.bundled-runtime` в
  `bb-app/server/dist/builtin-plugins/<имя>`. `.bundled-runtime` готовит
  `preparePluginRuntime` из `@bb/plugin-build`: собирает `dist/server.js`,
  `dist/app.js` с `*.meta.json` и пишет `package.json`, где `bb.server` и
  `bb.app` указывают на `./dist/*.js`, плюс навыки и значки.
- При запуске `reconcileBundled` ставит каждый встроенный плагин, которого
  нет, и обновляет версию и путь при новой версии приложения. Если такой id
  уже стоит из git или из папки, встроенный пропускается с предупреждением
  («already installed from …; skipping bundled reconciliation»).
- Удаление плагина из git или из папки стирает его строку вместе с
  настройками, секретами и расписаниями; удалённый встроенный помечается
  удалённым и больше сам не ставится.

## Предлагаемое устройство

1. **Сборка плагинов 1ma как встроенных, без изменения рабочей области bb.**
   Плагины 1ma не становятся пакетами рабочей области bb: иначе меняется
   `pnpm-lock.yaml` bb и `--frozen-lockfile` падает на каждом выпуске bb.
   После установки зависимостей bb наш шаг сборки:
   - копирует исходник каждого встраиваемого плагина из репозитория 1ma (тот
     же коммит, что серия правок) в каталог вне шаблонов рабочей области;
   - ставит его зависимости так же, как bb ставит плагин из git;
   - вызывает `preparePluginRuntime` самого bb (той же версии, что
     приложение), результат кладёт в `plugins/<имя>/.bundled-runtime`.
     Так плагин собран той же сборкой, тем же SDK, что встроенные плагины bb.
     Шаг один для Desktop, Desktop bb tests и пробной сборки нового bb.
2. **Правка bb `0014`:** имена плагинов 1ma в списке встроенных, с
   `autoInstall: true` и `defaultEnabled: true`. Тесты bb на список и
   наличие встроенных правятся в той же правке.
3. **Переход с установленных копий без потери настроек.** На Mac плагины 1ma
   стоят из git, на Linux из папки (`release-linux.mjs`). Варианты:
   - (а) рекомендую: та же правка `0014` учит `reconcileBundled` брать на
     себя плагин 1ma с тем же id, установленный из git или из папки, —
     переписать его строку на встроенный источник, сохранив настройки,
     секреты, расписания и данные. Только для id из списка встроенных 1ma.
   - (б) без изменения `reconcileBundled`: перед обновлением приложения
     записать настройки, удалить копии и после запуска вернуть настройки
     командой. Ручной шаг на каждой машине, легко потерять настройки
     переключателя серверов.
4. **Что меняется вокруг.**
   - `scripts/release-linux.mjs` выкладывает только невстроенные плагины;
     встроенные приходят с самообновлением сервера.
   - В `1ma-auto-updates` настройка «Update 1ma plugins» больше не касается
     встроенных: их версия — версия приложения.
   - Выпуск плагина 1ma = выпуск 1ma (сборка и публикация уже
     автоматические); теги `<plugin>/vX.Y.Z` остаются для установки на bb без
     1ma.
   - `inventory.json` ребрендинга не меняется: исходники плагинов 1ma не
     проходят через правила переименования bb.

## Решения по ревью Codex (14.11.2026)

Ревью Codex (коммит `0f73419`): пять находок по описанию, все приняты.
Устройство уточнено так.

1. **Две правки вместо одной.** `0014` — только сборка и список встроенных;
   `0015` — однократный переход с установленных копий. Так переход можно
   проверить и выпустить отдельно.
2. **Откат.** Прежняя версия 1ma не знает плагинов 1ma как встроенных и при
   запуске (`removeUnbundledBuiltins`) стирает их строки вместе с
   настройками, секретами и расписаниями. Обещаем откат только через снимок:
   `0015` перед первым переходом делает копию базы (`bb.db`, онлайн-копия
   SQLite) в `<data>/backups/before-1ma-builtins-<версия>.db`. Откат на
   версию до перехода — остановить 1ma, вернуть снимок, запустить прежнюю
   версию (шаг в инструкциях обновления Mac и Linux). Сценарий «новая → старая
   со снимком → новая» проверяется на копии данных в GitHub Actions.
3. **Файлы плагина.** `copyPluginRuntime` bb берёт `dist`, `skills` и
   объявленные значки, но не `assets` бренда (favicon, PNG для PWA) и не
   `themes` темы. Состав встроенного плагина = результат штатного
   `bb-plugin-build prepare-bundled` того же дерева bb плюс файлы из поля
   `files` его `package.json` (то, что вошло бы в `npm pack`); у каждого
   плагина 1ma `files` задан явно. Проверка: из собранного пакета сервера
   с недоступным исходным каталогом настоящими HTTP-запросами отдаются
   favicon, значки PWA и CSS темы.
4. **Сборка и кэш.** Исходники плагинов 1ma и их зависимости остаются вне
   рабочей области bb; зависимости ставятся по `pnpm-lock.yaml` 1ma с
   `--frozen-lockfile`; `prepare-bundled` вызывается штатной CLI bb из этого
   каталога, результат кладётся в `plugins/<имя>/.bundled-runtime` без
   `package.json` на уровне `plugins/<имя>`. Цепочка `bundled-plugins` →
   `bb-app` собирается с `--force` (как уже `smoke:tarball` и
   `desktop:build`), это проверяется тестом повторной сборки после правки
   только исходника плагина. Пути встраиваемых плагинов и `pnpm-lock.yaml`
   добавляются в фильтры Desktop и Desktop bb tests; шаг выполняется в
   Linux, Mac и тех шардах тестов bb, которые грузят встроенные плагины.
5. **Кого брать на себя (`0015`).** Только копию плагина 1ma с тем же id и
   проверяемым источником: из git — нормализованный репозиторий
   `github.com/1ma-ai/1ma` и подкаталог `plugins/<имя>` по сохранённому
   source intent; из папки — только установку `release-linux.mjs`, которая
   с этого шага кладёт в каталог плагина метку `.1ma-release.json`
   (репозиторий и коммит). Копия новее встроенной или с непроверяемым
   источником остаётся как есть со статусом-предупреждением. Переход
   переписывает поля источника, версии и активного артефакта, сохраняя
   включение, настройки, секреты, расписания и данные. Встроенные плагины 1ma,
   как и встроенные bb, не отключаются безопасным режимом: они часть
   продукта. Удалённый владельцем встроенный остаётся удалённым (метка bb);
   временно выключать — штатным отключением, оно хранит данные.
6. **Скрипт выкладки Linux.** `release-linux.mjs` пропускает встроенные
   плагины и отказывается трогать плагин со встроенным источником даже с
   `--replace-managed`. Известные отказы владельца (1ma Home Dashboard) не
   встраиваются.
7. **Порядок загрузки (`0013`).** Встроенные 1ma грузятся в группе встроенных
   по id; фабрики плагинов 1ma не ждут внешних ответов при загрузке; при
   приёмке `0014` проверяется холодный старт.

## Проверки

- Тесты сборочного шага на маленьком плагине-образце: `.bundled-runtime`
  совпадает по составу с тем, что bb делает для своих встроенных.
- Тест правки `0014` в bb: встроенный плагин 1ma берёт на себя копию из git и
  из папки, настройки на месте; чужой плагин с совпавшим id не трогается;
  удалённый пользователем встроенный не возвращается. Красный до правки.
- Сборка Desktop и Desktop bb tests зелёные; в собранном приложении в
  `builtin-plugins` есть плагины 1ma с `server.meta.json`.
- Сквозная проверка на GitHub (не на этой машине): чистый каталог данных —
  плагины 1ma стоят встроенными; каталог с копиями из git и из папки —
  после запуска они встроенные, настройки на месте.

## Вопросы для ревью

- Есть ли в bb путь проще, чем `preparePluginRuntime` вне рабочей области,
  и не ломает ли шаг кэш turbo (`bundled-plugins` не видит наших входов)?
- Безопасно ли взятие на себя по id; нужен ли признак источника (репозиторий
  1ma) вместо одного id?
- Что делать, если владелец позже удалит встроенный плагин 1ma: оставить
  удалённым, как у bb?
